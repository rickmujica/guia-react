Herramientas que no usás todos los días pero tenés que conocer: **vistas**, **procedimientos almacenados**, **triggers**, columnas **JSON**, y lo mínimo de administración (usuarios, permisos y backups).

## Vistas

Una **vista** es una consulta guardada con nombre, que se usa como si fuera una tabla. No guarda datos: cada vez que la consultás, MySQL corre la consulta de adentro.

<Consulta>

```sql
CREATE VIEW ofertas_detalle AS
SELECT o.id, o.titulo, o.seniority, o.modalidad, o.salario_max,
       e.nombre AS empresa, e.pais
FROM ofertas o
JOIN empresas e ON e.id = o.empresa_id;

SELECT titulo, empresa, salario_max
FROM ofertas_detalle
WHERE pais = 'PY' AND modalidad = 'remoto';
```

</Consulta>

Para qué sirven:

- **Esconder un join** que repetís en muchos lados.
- **Permisos**: le das a un usuario acceso a la vista (con algunas columnas) y no a la tabla entera.
- **Compatibilidad**: si cambiás las tablas, una vista con la forma vieja evita romper consultas existentes.

`CREATE OR REPLACE VIEW` la redefine y `DROP VIEW` la borra. Ojo con apilar vistas sobre vistas: el SQL final que ejecuta MySQL se vuelve difícil de seguir y de optimizar.

## Procedimientos almacenados

Un **procedimiento** es código SQL guardado en el servidor, con parámetros, que se ejecuta con `CALL`:

<Consulta>

```sql
CREATE PROCEDURE ofertas_remotas_desde(IN p_minimo INT)
  SELECT titulo, salario_max
  FROM ofertas
  WHERE modalidad = 'remoto' AND salario_max >= p_minimo
  ORDER BY salario_max DESC;

CALL ofertas_remotas_desde(4000);
```

</Consulta>

Con más de una sentencia, el cuerpo va entre `BEGIN` y `END` y puede tener variables, `IF` y bucles. En la consola de `mysql` hay que cambiar el **delimitador** para que el `;` de adentro no termine el `CREATE`:

```sql
DELIMITER //
CREATE PROCEDURE pasar_a_entrevista(IN p_postulacion INT, IN p_fecha DATETIME)
BEGIN
  UPDATE postulaciones SET estado = 'entrevista' WHERE id = p_postulacion;
  INSERT INTO entrevistas (postulacion_id, fecha, tipo) VALUES (p_postulacion, p_fecha, 'rrhh');
END //
DELIMITER ;

CALL pasar_a_entrevista(4, '2026-11-03 10:00:00');
```

`DELIMITER` es un comando de la consola, no de SQL: desde Node, un cliente gráfico o una migración, el `CREATE PROCEDURE … BEGIN … END` se manda tal cual.

<Nota title="¿Lógica en la base o en la aplicación?">
En empresas con mucho SQL (bancos, sistemas viejos) vas a encontrar mucha lógica en procedimientos. En aplicaciones modernas con Node, lo habitual es tener la lógica en el código de la aplicación (versionado, testeable, más fácil de leer) y usar la base para guardar y consultar. Los procedimientos se justifican cuando una operación mueve muchos datos y conviene no ir y volver por la red.
</Nota>

## Triggers

Un **trigger** se ejecuta solo, **antes o después** de un `INSERT`, `UPDATE` o `DELETE` en una tabla. Adentro, `OLD` es la fila como estaba y `NEW` como queda. Un uso típico: un historial de cambios.

<Consulta>

```sql
CREATE TABLE historial_estados (
  id               INT AUTO_INCREMENT PRIMARY KEY,
  postulacion_id   INT NOT NULL,
  estado_anterior  VARCHAR(20) NOT NULL,
  estado_nuevo     VARCHAR(20) NOT NULL,
  cambiado_en      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TRIGGER postulaciones_historial
AFTER UPDATE ON postulaciones
FOR EACH ROW
  INSERT INTO historial_estados (postulacion_id, estado_anterior, estado_nuevo)
  VALUES (OLD.id, OLD.estado, NEW.estado);

UPDATE postulaciones SET estado = 'rechazado' WHERE id = 1;
UPDATE postulaciones SET estado = 'oferta' WHERE id = 5;

SELECT postulacion_id, estado_anterior, estado_nuevo
FROM historial_estados
ORDER BY id;
```

</Consulta>

<Ojo title="Usalos con medida">
Un trigger es lógica **invisible**: alguien hace un `UPDATE` y pasan cosas que no están en ningún lado del código de la aplicación. Son buenos para auditoría e historial. Para validar datos, primero mirá si alcanza con un `CHECK`, un `NOT NULL` o una clave foránea (MySQL respeta los `CHECK` desde la 8.0.16).
</Ojo>

## Columnas JSON

MySQL tiene un tipo `JSON`: valida que el contenido sea JSON y tiene funciones para leerlo. Sirve para datos con forma variable que no vale la pena normalizar (preferencias, metadatos):

<Consulta>

```sql
ALTER TABLE ofertas ADD COLUMN extra JSON NULL;

UPDATE ofertas
SET extra = '{"beneficios": ["prepaga", "equipo"], "zona_horaria": "UTC-3"}'
WHERE id = 1;

SELECT titulo,
       extra->>'$.zona_horaria' AS zona,
       JSON_LENGTH(extra->'$.beneficios') AS beneficios
FROM ofertas
WHERE extra IS NOT NULL;
```

</Consulta>

`->` devuelve un valor JSON y `->>` lo devuelve como texto (sin comillas). Y al revés, se puede **armar JSON** desde una consulta, muy útil para devolver datos anidados a una API en una sola consulta:

<Consulta>

```sql
SELECT e.nombre,
       JSON_ARRAYAGG(JSON_OBJECT('titulo', o.titulo, 'salario', o.salario_max)) AS ofertas
FROM empresas e
JOIN ofertas o ON o.empresa_id = e.id
WHERE e.pais = 'UY'
GROUP BY e.id, e.nombre;
```

</Consulta>

No abuses: lo que filtrás, ordenás o unís seguido va en columnas normales. Un `WHERE` sobre un campo de un JSON no usa índices (salvo que crees una columna generada indexada).

## Usuarios y permisos

Tu aplicación **no** se conecta como `root`. Se crea un usuario con los permisos justos (**principio de mínimo privilegio**): si alguien roba la contraseña o encuentra una inyección SQL, el daño queda limitado.

```sql
CREATE USER 'app_busqueda'@'%' IDENTIFIED BY 'una-clave-larga-y-aleatoria';

-- Solo leer y escribir datos de una base. Sin DROP, sin ALTER, sin otras bases.
GRANT SELECT, INSERT, UPDATE, DELETE ON busqueda.* TO 'app_busqueda'@'%';

SHOW GRANTS FOR 'app_busqueda'@'%';
REVOKE DELETE ON busqueda.* FROM 'app_busqueda'@'%';
DROP USER 'app_busqueda'@'%';
```

El `@'%'` es desde dónde se puede conectar: `'localhost'` solo desde la misma máquina, `'%'` desde cualquier lado. Las migraciones (que crean y alteran tablas) usan otro usuario con más permisos.

## Backups

`mysqldump` exporta una base como un archivo `.sql` con los `CREATE TABLE` y los `INSERT`:

```bash
# Exportar (--single-transaction: una foto consistente sin bloquear las tablas InnoDB)
mysqldump -u root --single-transaction busqueda > busqueda-2026-10-30.sql

# Restaurar en otra base
mysql -u root -e "CREATE DATABASE busqueda_copia"
mysql -u root busqueda_copia < busqueda-2026-10-30.sql
```

Para bases grandes hay herramientas más rápidas (MySQL Shell con `util.dumpInstance`, o los snapshots del proveedor de la nube). Lo importante: un backup que nunca probaste restaurar no es un backup.

<Entrevista>
"¿Qué es una vista y en qué se diferencia de una tabla?" → "Una consulta guardada con nombre que se usa como tabla, pero no guarda datos: se ejecuta cada vez. Sirve para reutilizar joins y para dar acceso a una parte de los datos sin dar acceso a la tabla. Si necesito los resultados guardados para leer rápido, eso es una vista materializada, que MySQL no tiene: se arma con una tabla que se actualiza con un job o un trigger."
</Entrevista>
